# 评论分析数据口径

## 数据源与字段

- 数据源：`有效评论TOP10.xlsx` 的“天猫_评论”工作表。
- 原始记录：22,820 条，覆盖 12 个品类、71 家店铺。本批次已达到当前能抓取的类目上限；后续未更新的类目可能不再更新。
- 使用字段：商品ID、店铺、品类、初评时间、初评、有用、追评、追评时间。
- 源文件没有平台星级，因此看板不发布真实满意度或店铺星级。

## 两套去重口径

- 顶部的 19,867 条是审计口径：先排除 1,344 条空白、过短或明显垃圾文本，再对全部可用文本做全局精确去重。
- 筛选模块采用分析管道口径：排除不足 4 个有效字符的文本，再在当前品类、月份和店铺范围内做精确去重。
- 相同文本可能出现在不同品类或不同月份，因此类目数、月度数不能直接相加后与全局去重数比较。

## 月份格式

源字段按日期读取，再统一输出为 `YYYY年M月`，例如 `2026年5月`。月份排序依据年份和月份数值，而不是字符串排序。

## 文本体验分

文本体验分不是平台星级。计算步骤：

1. 对当前筛选范围的去重评论匹配正向和风险表达词。
2. 正向表达率 = 正向词数量高于风险词数量的评论数 ÷ 当前去重评论数。
3. 风险提及率 = 至少命中一个风险词的评论数 ÷ 当前去重评论数。
4. 文本体验分 = `3 + 0.02 ×（正向表达率 - 风险提及率）`，结果限制在 1–5 分。
5. 少于 30 条时不展示体验分、正向率和风险率，也不参与品牌排名。

## 主题与代表评论

- 主题、人群、场景、目的和关键词均由预先公开在构建脚本中的词组规则匹配。
- 主题提及率的分母是当前筛选范围内的精确去重评论，不是低星评论。
- 每个主题最多保留两条代表评论；排序综合考虑主题词命中、正负表达信息量和“有用”票数。
- 有用票只用于代表评论排序，不用于放大主题提及率或文本体验分。
- 核心痛点使用类目专属问题词组聚类，同时展示命中量、提及率、可能机制、业务影响与代表原评；“差”等泛化单字不再单独作为分析结论。
- 品牌比较仅在同类目、同月份和相同文本规则下进行；少于30条的店铺不参与比较。雨虹仅在源数据确有对应店铺的类目中高亮。
- 交互评论列表来自当前类目内的可用、精确去重初评，并继续受年月与店铺筛选约束；关键词、目的、人群和场景通过同一套公开词组规则回溯，不把未命中的评论塞入证据列表。
- 源文件没有星级字段。评论抽屉只展示文本体验分并标注“非平台星级”，不生成或伪造星级。
- 核心痛点为每个类目使用专属问题词组，并展示当前年月与店铺筛选下的全部命中、有效、精确去重评论。明确的正向否定表达会从痛点中排除，例如“防止反味、没有反味”不计入“排水与防臭冲突”。

## 样本可信度

- 少于30条：探索性，仅展示评论内容，不排名。
- 30–99条：方向性证据，谨慎比较。
- 100条及以上：可作为优先信号，但仍需检查重复、产品集中和文本覆盖。

## 重新生成

安装 `pandas` 与 `openpyxl` 后执行：

```bash
python scripts/build_dashboard_data.py /path/to/评论.xlsx data
```

脚本生成一个小型 `data/manifest.js` 和12个 `data/categories/*.js` 文件。页面首屏只读取清单和当前类目，切换类目时再按需加载。使用脚本资源而不是 `fetch(JSON)`，因此既支持GitHub Pages，也支持直接双击本地 `file://` 页面。

生成后应检查：12个品类是否齐全、月份范围、各片段样本量、体验分范围、主题提及率范围以及代表评论可追溯标签。
